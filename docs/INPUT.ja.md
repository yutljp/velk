# 生バイト列とパックされた実行ファイル

[English](INPUT.md)

## ヘッダーのないコード

命令セットとロードアドレスを明示します。

```sh
velk -D --raw-arch x86_64 --load-address 0x7000 code.bin 0x7000
```

`--raw-arch` は `x86_64`、`i386`、`aarch64`、`arm32`（A32）、`thumb`
（T32）に対応します。認識可能なオブジェクトヘッダーを持つファイルは対象外です。
バイト列を `raw` という単一の読み取り・実行可能領域として配置します。
先頭バイトの仮想アドレスは `--load-address` です。`--entry ADDRESS` を繰り返すと
関数の入口を複数指定できます。省略時はロードアドレスが入口になります。
既存のプロローグ検出も実行します。ARM の入口アドレスの最下位ビットが 1 なら
Thumb として扱い、物理アドレスからはそのビットを除きます。ARM と AArch64 の
ロードアドレスには命令のアラインメントが必要です。32 ビットのマッピングは
32 ビットのアドレス空間に収める必要があります。不正な入口やアドレスの
オーバーフローはエラーになります。

バイト順序の既定値はリトルエンディアンです。`--raw-byte-order big` はエラーを
返します。ビッグエンディアンの生コードには対応していません。呼び出し規約は
x86-64 が System V、i386 が cdecl、AArch64 が AAPCS64、ARM32/Thumb が
AAPCS32 です。生バイト列から OS やインポートテーブルを推定しません。
再配置と外部コード・データの参照は入力イメージで解決されている必要があります。

スクリプトでは `velk.open` に同じ情報を渡します。

```js
const b = velk.open("code.bin", {
  raw: {arch: "x86_64", base: "0x7000"}
});
b.getFunction("0x7000").decompile();
```

`raw.entries` は省略可能な入口アドレスの配列で、`raw.byteOrder` の既定値は
`"little"` です。JavaScript が整数を正確に扱える範囲を超えるアドレスには文字列を
使ってください。マッピングごとに独立したセッションキャッシュを使います。
文字列は生領域内で検索します。検索、相互参照、メモリ読み取り、エミュレーションは
仮想アドレスを使います。エミュレーションは実行可能なバイト列を保護するため、
生領域への書き込みはメモリエラーになります。変更する入力バッファーには
エミュレーションのヒープまたはスタックを使ってください。関数の注釈を保存するとプロジェクトファイルに生領域の
マッピングも保存され、そのプロジェクトを指定すればオプションの再指定なしで
開けます。プロジェクトと異なるマッピングを明示するとエラーになります。
別のマッピングには別のプロジェクトを使ってください。

MCP では `velk_run_script` でこの JavaScript の例を実行できます。
`velk_emulate` にも `path`、`start`、`options` とともに `raw` を渡せます。

## UPX の展開

UPX を検出した ELF または PE を開くと、まず velk 内蔵のデコーダーを使います。
入力の実行ファイルは実行しません。NRV2B、NRV2D、NRV2E（32 ビットとバイト単位の
ビットストリーム）、および UPX のプロパティーが `1a 03` の LZMA に対応します。
LZMA の展開には `lzma-rs` を使います。対応する形式は x86-64、i386、AArch64、
ARM32 のリトルエンディアン ELF と、x86-64、i386 の PE です。分岐フィルター
`0x26`、`0x46`、`0x49`、`0x50`（ARM）、`0x52`（AArch64）と、フィルターなしの
ブロックを扱います。x86 の分岐フィルターの範囲は 16 MiB までです。他のヘッダー
パラメーター値には外部フォールバックを使います。

ELF では保存されたプログラムヘッダー、ロードセグメント、隙間と残りのファイルを
復元します。標準のプログラムヘッダー配置で、ロードセグメントが順に並び、重ならず、
最初のセグメントにヘッダーが含まれることが必要です。PE では保存された元のヘッダーと
セクション、元のエントリーポイントを復元し、名前・序数によるインポートと
HIGHLOW または DIR64 のベース再配置を組み直します。フィクスチャでの参照デコーダーと
同様に、PE のデバッグと IAT のディレクトリー項目を消去し、インポートのヒントをゼロに
して、独立したルックアップテーブルを作らずに復元します。これらの元の情報は戻りません。

他の UPX ヘッダー配置、圧縮方式、フィルター、LZMA プロパティーには、PATH 上の
`upx -d` をフォールバックとして使います。PE のリソース、TLS、ロード構成、バインド済み・
遅延インポート、CLR メタデータ、ファイルのオーバーレイ、他の再配置の符号化にも
フォールバックが必要です。不正なサイズ、切り詰められたブロック、チェックサムの不一致は
エラーになります。途中までの復元ファイルは返しません。成功した出力は元と同じ形式として
解析でき、エントリーポイントを持つことを確認してから通常のローダーで扱います。

入力と復元ファイルは各 128 MiB までです。ブロックの出力と LZMA の辞書にも上限を設けます。
複数のバッファーが同時に存在する場合があります。外部フォールバックに対応する OS は
Linux と macOS です。子プロセスには CPU 時間 5 秒、経過時間 10 秒の制限を設け、
コアダンプを無効化します。Linux では子プロセスのアドレス空間を 512 MiB に厳密に制限します。
macOS では常駐メモリを 1 ミリ秒ごとに調べ、512 MiB を超えると子プロセスを終了します。
この監視には超過の余地があります。

検出には識別子と既知の ELF・PE ヘッダー構造を使います。テストでは `UPX!` の置換と
PE セクション名の変更も確認します。形式を示すフィールド自体を削除・変更すると、
構造からの検出ができない場合があります。他のパッカーには対応していません。
CLI は標準エラー出力にパッカー、識別情報に含まれるバージョン、使ったデコーダーを表示します。
スクリプトでは `b.packing` に同じ情報が入り、通常の入力では null です。

展開済みの実行ファイルを保存しながら解析できます。

```sh
velk -D --save-unpacked recovered.exe packed.exe add3
```

```js
const b = velk.open("packed.exe");
b.saveUnpacked("recovered.exe");
b.getFunction("add3").decompile();
```

保存には展開の成功と、まだ存在しない保存先が必要です。解析用の再配置を適用する
前の、デコーダー出力全体を保存します。
`tests/data/upx` の自作フィクスチャは、上記の全形式・アーキテクチャと四つの圧縮方式、
PE のインポートと再配置、分岐フィルターを含みます。復元したバイト列を `upx -d` の出力と
比較し、ELF では元のファイルとの一致も確認します。
`bash tools/make_upx_fixtures.sh OUTPUT_DIRECTORY` で再生成できます。
追加のパック処理のテストには PATH 上の UPX が必要で、CLI、JavaScript、MCP、保存と
出力 C のコンパイル・実行を確認します。保存済みフィクスチャとデコーダーの性質のテストには
UPX は不要です。これらの確認は Linux で実行しました。ここでは macOS は未確認です。
